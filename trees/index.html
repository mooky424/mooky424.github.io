B-trees vs. LSM-trees: The backbone of modern storage engines

As modern data needs become more and more demanding, a focus on the efficiency of storing and searching through data storage becomes critical. In this comparative review, we will be looking at two of the most used data structures in modern storage engines, namely B-trees and LSM-trees.

The interface and the tree are separate choices.
System SQL / NoSQL Tree
PostgreSQL SQL B-tree
InnoDB SQL B-tree
SQLite SQL B-tree
MongoDB NoSQL B-tree
Cassandra NoSQL LSM-tree

How they differ

Aspect B-tree LSM-tree
Primary strength Stores multiple keys in a single node to efficiently store and retrieve keys from external storage Buffers writes in memory and flushes sequentially for high write throughput
Tradeoffs In-place updates can cause random I/O and higher write overhead May require reading multiple files to find a specific key (especially if the key is old)

B-trees

A B-tree is a type of self-balancing tree data structure that leverages how external storage devices (like disk drives) store data in large chunks. Different from a regular BST, a B-tree allows for more than one key per node and more than two children per node.

Properties

A B-tree of order m is a search tree whose nodes have at most m children, and each node has at most m-1 keys

  1. Every leaf is at the same depth.
  2. Keys in each node are sorted in ascending order (relevant for searching the tree).
  3. All nodes (except root) have at least m/2 - 1 keys and m/2 children.
  4. The root holds at least one key. If it is the only node, it has no children. If it has children, it has at least two.
Operation Time
Search O(log n)
Insert O(log n)
Delete O(log n)
Traverse O(n)
  1. Start at the root and walk down.
  2. If the node contains the key, stop. That is the node.
  3. If not, compare the key with the sorted keys and choose a child.
    • Smaller than every key: the leftmost child.
    • Larger than every key: the rightmost child.
    • Between two keys: the child between them.
  4. Repeat until the key is found, or the node has no children.

  1. Walk the tree to the place the new key belongs.
  2. Then one of three cases.
    1. The node has room.
      • Insert the key in the node.
    2. The node is full, but the parent has room.
      • Add the new key into the node.
      • Split the node around the middle key.
      • Move the middle key into the parent.
      • Keys smaller than the middle key stay in the left child.
      • Keys larger than the middle key go in a new right child.
    3. The leaf and its parent are both full.
      • Repeat the split upward until a node has room.

  • Key that moved
  • Full, or almost empty

  1. If the key is in a leaf, remove it.
  2. If the key is in an internal node, do one of three things.
    1. The left child has at least m/2 keys.
      • Swap the key with the greatest key to its left, then remove that copy below.
    2. Otherwise, if the right child has at least m/2 keys.
      • Swap the key with the smallest key to its right, then remove that copy below.
    3. Both children have only m/2 - 1 keys.
      • Merge the two children.
      • Move the key down between them.
      • Remove it from the merged node.
  3. If the key is farther down, do not enter a child that has only m/2 - 1 keys. Fix it first.
    1. A sibling has at least m/2 keys: borrow. A key from the sibling moves up into the parent, and the parent key between them moves down.
    2. Both immediate siblings have only m/2 - 1 keys: merge the child with one sibling. The parent key between them comes down.
  4. If the root is left with no keys, drop it. Its only child becomes the new root, and the tree gets shorter.

LSM-trees

An LSM-tree (Log-Structured Merge-tree) is a write-optimized data structure that turns random disk writes into fast, sequential writes by buffering changes in memory and flushing them to disk as immutable sorted files. Different from a B-tree, which updates records in place on disk, an LSM-tree appends and merges sorted runs in the background.

Properties

An LSM-tree is a multi-level data structure composed of a mutable in-memory buffer (C0) and a hierarchy of immutable, sorted on-disk components (C1, C2, …, Ck) with an exponential size ratio T.

  1. Data is never modified or deleted in place on disk; all updates and deletes (tombstones) are appended as new entries.
  2. Keys within the in-memory memtable and within each on-disk sorted run (SSTable) are maintained in ascending order.
  3. Each disk level Ci has a maximum capacity T times larger than the preceding level Ci−1 (where T is the size ratio or fanout).
  4. Newer data resides in upper levels (memory and shallow disk levels), while older data migrates to deeper levels through background compaction.
  5. Within any single disk level Ci (i ≥ 1) in a standard leveled LSM-tree, SSTables hold strictly disjoint key ranges, though key ranges may overlap across different levels.
Operation Time
Search O(log n)
Write O(1)
Traverse O(n)

Unlike B-trees, LSM-trees buffer recent writes in an in-memory data structure (such as a skip list or balanced search tree) before writing them to disk. Keeping recent keys sorted in memory absorbs fast updates and makes the newest data quick to read without immediate disk I/O.

  1. A new key is written into memory, in sorted order. Older SSTables are not opened.
  2. If that key is already in memory, its copy is replaced.
  3. If an older SSTable has the key, the new copy goes in memory and the old one stays.
  4. A delete is the same write, marked ×key. The older copy stays until compaction.

When the memtable reaches a configured size limit, it flushes to disk as a Sorted String Table. Flushing turns accumulated in-memory writes into durable, sorted on-disk data so memory can be reused.

  1. Memory holds only as many keys as its size limit.
  2. The key that fills it is written in. Then the whole table is saved to disk as an SSTable, and memory is cleared.
  3. If memory is already full, it is saved first. The new key starts the next table.

Compaction is a background process that reads multiple SSTables, merges their sorted entries, discards overwritten values and deleted markers (tombstones), and writes out new consolidated SSTables. This keeps the number of files manageable, reclaims disk space, and prevents read lookups from having to check too many overlapping files.

  1. C1 holds at most T times the memtable, where T is the size ratio.
  2. A flush past that limit merges C1 into C2.
  3. C2 holds T times C1. Past that, it merges into C3.
  4. The newest copy of each key is kept. A ×key is dropped on the oldest level.
